# Response Document Format

Produces filing-ready office action responses. This skill defines the document skeleton; firm-specific values live in `references/firm-profile.md` — read it first and substitute throughout. If no firm profile exists, ask the user for letterhead details once and offer to save them.

## Document skeleton

ALWAYS use this structure, in this order:

1. **Caption block** — render this exact template with EVERY field filled (see "Caption fields" below for sources). An empty or bracket-placeholder field in a generated document is a defect, not an option:

   ```
   IN THE UNITED STATES PATENT AND TRADEMARK OFFICE

   Application No.:   {application_number}
   Filing Date:       {filing_date}
   First Named
   Inventor:          {first_named_inventor}
   Art Unit:          {art_unit}
   Examiner:          {examiner}
   Confirmation No.:  {confirmation_number}
   Attorney Docket
   No.:               {docket_number}
   Title:             {title}
   ```
2. **Title line** — e.g., "AMENDMENT AND RESPONSE UNDER 37 C.F.R. § 1.111" (non-final) or "...§ 1.116" (after final). Match the OA posture from `oa_review`.
3. **Opening paragraph** — responsive-to sentence identifying the OA by mailing date; extension-of-time statement if applicable.
4. **Amendments to the Claims** — begins on a new page. Use the `oa_amendment_listing` output — generated from the confirmed response plan's proposals so the markup carries provenance — exactly as generated (the server already applies 1.121 element line-breaking; see "Claim formatting"). Include the standard 1.121(c) preamble sentence.
5. **Remarks** — status-of-claims paragraph first (claims pending, amended, canceled, new). Then address objections before rejections; rejections in order §112 → §101 → §102 → §103; double patenting last. One heading per ground, identifying the statute, claims, and references.
6. **Conclusion** — allowance request, interview invitation, fee authorization sentence charging any deficiency to the firm's deposit account (from firm profile).
7. **Signature block** — /typed signature/ format, attorney name, registration number, firm name/address/phone, date.

## Caption fields — sources and the no-blanks rule

| Field | Source |
|---|---|
| Application No., Filing Date, First Named Inventor, Art Unit, Examiner, Confirmation No., Title | `matter_open` caption (the USPTO record). Call it fresh in this session — do not carry values from an earlier conversation. |
| Attorney Docket No., Customer No., correspondence address | Usually IN the wrapper: check the Filing Receipt and BIB sheet (`matter_documents` → `matter_read`) before asking. Only if genuinely absent from the wrapper AND the firm profile, ASK the user — never guess and never leave it blank. |
| OA mailing date (opening paragraph) | `oa_review` / `matter_open` — the wrapper record, never user memory. |

**Pre-flight check (mandatory, immediately before generating the document):** list every caption field with the value you are about to insert and its source. If ANY value is missing, stop and ask the user for it — do not generate a document containing `[Art Unit]`, `TBD`, or an omitted line. This check exists because the most common assembly defect is a skipped caption variable.

## Claim formatting (applies EVERYWHERE claim text is rendered)

Claims are never rendered as one continuous sentence. Server tool output (`oa_amendment_listing`, `claims_get`) arrives with 1.121 element formatting already applied — line break after the preamble's `:` and after every element-ending `;` / `; and`, each element first-line-indented. **Use it as generated**: never reflow, re-wrap, or "clean up" the text or its markup; preserve every character including the line breaks.

For claim text you render from any other source (e.g., a claim quoted in Remarks from a paper excerpt), apply the same convention yourself — break after `:` and each element-ending `;` or `; and`, indent each element (tab or 0.5"), keep the claim number + status identifier on the first line with the preamble:

```
1. (Currently Amended) A vehicle control system comprising:
        a sensor configured to detect an obstacle;
        a controller coupled to the sensor; and
        a display that renders an alert generated by the controller.
```

**Document styling of clauses (attorney convention):** each element is its own
paragraph with a FIRST-LINE indent (0.5") only — continuation lines of a
wrapped clause sit flush to the left margin. Never block-indent the whole
clause. Claim number + status identifier stay flush left with the preamble.

## Who generates the document

**The server does. Always.** Call `oa_response_document` with the confirmed plan
revision id, the docket number, and the signature block (attorney name +
registration number from the firm profile; ask the user once if unknown). It
renders this skill's entire skeleton server-side — caption, 1.111/1.116 title,
the verified 1.121 listing with real underline/strike formatting, Remarks
scaffolded from the approved plan, conclusion, signature — validates its own
formatting, and returns a download link. It works in every Claude environment
including claude.ai web, with no local document tooling involved. The server
refuses and names the missing field if a caption value is absent (it never
generates blanks), and refuses on a draft (unconfirmed) revision.

**Never assemble a filing paper yourself** — not with the `docx` skill, not with
python-docx, not by any other route, and not when the user asks for "the claims
in Word". A hand-built paper is substantively accurate and formally wrong, which
is the failure mode that looks filing-ready: it has passed as filing-ready in
this product before. Everything in this skill describes what the SERVER emits so
you can check it, not a recipe for you to follow.

If `oa_response_document` is genuinely unavailable (a v1-only surface), you may
produce **markdown only** — never a .docx — and it must open with a plain
banner: `NOT A FILING DOCUMENT — generated without the server renderer; formatting
is not verified.` Say the same thing to the user in your reply.

## Formatting rules

- 1.5 or double spacing in Remarks; single spacing within a claim, with element breaks per "Claim formatting"; one blank line between claims.
- Claim amendment markup is sacrosanct: underline additions, strike-through deletions, correct status identifiers. Never regenerate this by hand — if the base claims change, regenerate through `oa_amendment_listing` (it will refuse on a stale proposal; re-confirm the plan first).
- Page numbers bottom center; caption page unnumbered per firm profile preference.
- Strip all internal pkb:// verification URIs from the client/filing document. Preserve them in a separate attorney-review memo if the user wants one.
- Remarks arrive as a scaffold of the approved strategies: tell the user to review and expand them in Word — the server never invents argument prose.

## Voice

- Formal, direct, no hedging in the traversal ("The Office Action errs...", "Reference X does not disclose..."). Reserve conditional phrasing for alternative arguments expressly framed as such.
- Refer to "the Office Action," "the Examiner" (capitalized), "Applicant" (no article, per firm convention — check firm profile).
- No em dashes in filed documents; use commas or parentheticals.
